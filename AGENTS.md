# Repository instructions

## Local development storage target

Read [docs/development-storage-policy.md](docs/development-storage-policy.md) before installing dependencies, building, running native tests, creating worktrees, or generating large artifacts.

- All local development for this project shares one **20,000,000,000-byte (20 GB)** retained-storage limit after housekeeping across worktrees, drives, dependencies, caches, Docker resources, test images and delivery artifacts. This is not a per-agent or per-directory allowance or a limit on temporary build space.
- Prioritize build speed. Measure before and after storage-intensive work and check actual disk free space. Compilation, installation and testing may temporarily exceed 20 GB when the disk has sufficient room. Never interrupt compilation or clear active caches solely because of this limit. After the build finishes (success or failure), measure again; automatically reclaim confirmed unused outputs only if retained usage exceeds 20 GB. Keep compatible warm caches when within the limit; an explicit post-build cleanup request remains supported.
- Never claim the retained limit is satisfied when usage remains above 20 GB or accounting is incomplete. Report the remaining excess or unverified paths; preserve source, required data and active/unknown-owner caches rather than deleting them to force a number.
- The 2026-11-01 cleanup left approximately 8.61 GB across project worktrees and dedicated external build paths. Shared SDK/toolchain/Docker storage remains separately reported; this baseline alone does not prove that every project-attributable resource fits the budget. Preserve necessary data and avoid redundant outputs.
- Count project outputs on other drives, `%TEMP%`, Docker and other worktrees in the same retained total. Choose suitable build paths for speed and sufficient actual free space; moving an output does not remove it from accounting.
- Share compatible dependency caches; use one designated writer for shared build outputs. Never copy emulator disks as test evidence. Keep only the latest APK and one verified rollback version as the retention target; do not delete existing versions merely because this policy was added.
- Use `scripts/Build-Android.ps1` for APK packaging. It measures before/after, checks actual free space and runs safe housekeeping after building/publication; keep external project paths registered in the ignored `.tada-storage.local.json`. Inspect `artifacts/packaging-storage.json` for skipped cleanup, incomplete accounting or retained-target warnings. Never bypass these checks by invoking Gradle and publishing manually without equivalent verification.
- Packaging is not finished until storage housekeeping is checked: verify the new package and latest aliases first, retain the new latest plus one verified rollback, measure retained usage and only reclaim rebuildable caches after the build if it exceeds 20 GB (or cleanup was explicitly requested). Keep warm caches below the limit. Retention cleanup of obsolete generated packages remains safe after publication. Remeasure after cleanup and report the retained total. Failed packaging must preserve the last working latest and rollback. Skip active or unknown-owner files rather than guessing.
- Cleanup must preserve source changes, databases, uploads, credentials, signing material, current/rollback releases and required evidence. Verify resolved absolute paths and ownership before deletion; never prune shared Docker resources indiscriminately.
- Preinstalled shared SDKs and toolchains are reported separately. Do not claim that this project budget limits the entire computer or that a document provides an operating-system disk quota.

## Agent behavior regression

After changing prompts, query rewriting, tool discovery, tool argument binding or the agent execution loop, run `pnpm --config.verify-deps-before-run=false run bench:product` from `services/agent` with the configured model. Check per-case regressions, completion, tool hits and latency against the last compatible report. Use the same fixed suite for before/after comparisons. Add a fixture for a reproduced product issue when the existing suite does not cover it. See [the scenario runner](services/agent/README.md#妥啦场景回归).
