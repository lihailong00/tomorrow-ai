# today.ai 对齐产品：技术路线独立审阅

研究日期：2026-10-26。本文是拟建产品的工程建议，不代表 today.ai 的内部技术实现，也不把公开宣传等同于可验证的执行效果。最终范围还需要以实际可访问的产品流程校准。

## 1. 建议先定下的边界

第一版交付“会记住用户、能够主动提出有依据的建议、能够在用户离线时完成受控任务”的 Web 产品。优先实现五个闭环：每日简报、会议前准备、邮件草稿、文件问答、定期研究与提醒。连接器先做 Gmail、Google Calendar、Google Drive，按只读接入、生成草稿、批准后写入的顺序开放。

第一版应有：流式对话、文件上传与结果下载、任务列表与进度、可解释的记忆管理、建议收件箱、单次与周期任务、Google 授权和撤销、任务取消、执行审计、受控网页读取。语音输入可做异步转写；实时语音、任意桌面操作、移动端远程控制、开放社区代码技能不应同时进入首版关键路径。

“几乎一致”需要拆为功能一致度、交互一致度、视觉一致度、执行能力一致度四张验收表。完成高保真的界面不能证明记忆、主动性或执行可靠性已达到同一水平。建议独立品牌与资产，按真实操作流程对齐体验。

## 2. 最小可持续架构

采用模块化单体 API + 独立异步 Worker，而非一开始拆成大量微服务。建议 TypeScript Web 前端、TypeScript API 与 Temporal Worker；只有文件解析、OCR 或特殊模型处理确有需要时再引入 Python Worker。

| 层 | 建议 | 关键职责 |
|---|---|---|
| 客户端 | React / Next.js Web，响应式布局 | 对话、记忆页、建议、计划、任务轨迹、审批卡片 |
| 应用 API | 单体中的身份、对话、任务、连接器、记忆模块 | 验证身份、资源授权、版本控制、流式事件 |
| 持久任务 | Temporal；优先评估托管以减少运维 | 等待审批、重试、超时、定时、断点恢复、取消 |
| 业务数据库 | PostgreSQL + pgvector + 全文检索 | 业务真相、来源与权限、操作账本、混合检索 |
| 文件 | S3 兼容对象存储 | 上传、解析产物、用户导出；签名 URL 有效期受控 |
| 模型网关 | 多供应商适配、按任务路由 | 模型预算、结构化输出、重试规则、追踪与限流 |
| 工具执行 | 明确 schema 的连接器 + 独立浏览器/代码沙箱 | 权限校验、凭据代理、资源限制、输出审查 |
| 观测 | 结构化审计、指标、分布式 trace、评测集 | 每任务费用、耗时、失败类型、模型与工具版本 |

Redis 仅在出现明确需求时承担短期缓存、速率限制或流式事件转发；它不应成为任务和审批唯一存储。暂不需要 Kubernetes、独立向量数据库、自训大模型、多层 Agent 群和图数据库。复杂度先花在权限、可恢复任务和数据来源上。

Temporal 工作流应只编排确定性控制流；模型调用、外部 API 和数据库访问放在 Activity 中。工作流升级需考虑重放兼容和版本策略。[Temporal 工作流定义](https://docs.temporal.io/workflow-definition)

## 3. 关键数据对象

所有用户数据均带 `tenant_id`、所有者、创建时间、版本号与删除状态。

- `User / Workspace / Membership`：用户、租户、成员角色、时区与通知偏好。
- `Conversation / Message / Attachment`：消息、附件、模型版本、可引用的内容来源。
- `ConnectorAccount / Grant / SecretRef / SyncCursor`：账号、实际授权范围、密钥引用、历史游标、订阅到期时间、同步状态。
- `SourceDocument / Chunk / SourceACL / SourceVersion`：原始来源、分块、来源访问控制与更新时间。
- `MemoryItem / MemoryEvidence / MemoryRevision`：事实、偏好、有效期、置信度、证据、被替代关系、用户纠正。
- `Suggestion / TriggerEvent / Feedback`：触发原因、关联证据、去重标识、采纳/忽略、打扰预算。
- `Task / TaskRun / Step / Artifact`：任务定义、某次运行、步骤、结果与成本。不要用一次聊天消息代替任务状态。
- `Schedule`：原始自然语言、规范化规则、IANA 时区、下一次时间、错过补跑和并发策略、版本。
- `ActionProposal / Approval / OperationLedger`：待执行动作、批准内容哈希、有效期、逻辑操作 ID、外部资源 ID、执行结果。
- `Device / DeviceSession / CapabilityGrant`：后续桌面端配对、设备在线状态、短期能力票据。
- `SkillPackage / SkillVersion / CapabilityManifest`：技能内容、固定版本、来源、声明权限、安装批准与撤回状态。
- `DeletionRequest / Tombstone / AuditEvent / UsageLedger`：删除闭环、阻止重摄入、审计与计费。

第一版可以合并部分表，但不应省略来源、权限、版本、逻辑操作 ID、删除状态这些字段。

## 4. 记忆要做成可纠正的数据系统

建议链路：授权来源摄入 → 按权限解析 → 生成候选记忆 → 去重与冲突检测 → 保存证据和版本 → 检索时按租户、来源权限、有效期过滤 → 回答时引用。

区分用户明确要求记住的事实、模型从历史推断的偏好、临时任务状态。推断不能静默成为永久真相；界面应允许查看、修改、删除、暂停自动记忆，显示“为何记住”和来源。新来源覆盖旧记忆应保留修订关系；陈旧事件不能继续当作当前偏好。

首版用 PostgreSQL 全文检索 + 向量相似度 + 时间/来源权重即可。pgvector 支持精确检索和 HNSW/IVFFlat 近似检索；近似索引的过滤会影响召回，应在租户过滤条件下实测，必要时使用精确查询、迭代扫描或分区，而非直接堆一个全局 HNSW 索引。[pgvector 官方说明](https://github.com/pgvector/pgvector)

删除必须立即阻止后续检索，再异步清理原文副本、分块、向量、摘要、缓存、导出和模型可访问的历史。只删除一条 `memory` 行不能代表被遗忘。撤销连接器后停止摄入与执行，并明确用户是否保留已导入资料；尊重源文档权限变更。针对已删除记忆，应防止连接器下次同步时重新生成；恢复备份时也要重放删除标记。

工作流和追踪系统不能成为遗漏的敏感数据副本。Temporal 默认序列化的 payload 会保存在事件历史中；应尽量只传对象引用和最少参数，敏感 payload 加密，配置保留期与外部 payload 清理。日志、错误信息和搜索属性也不能放令牌或正文。[Temporal 数据处理](https://docs.temporal.io/develop/typescript/best-practices/data-handling)

## 5. 主动性需要触发和预算

不要让高价模型持续读取用户所有数据。建议采用事件触发：新邮件、日历临近、任务状态变化、用户日程规则 → 轻量规则筛选 → 候选聚合与去重 → 检索必要上下文 → 模型判断是否值得建议 → 通知。

每条建议要能解释触发依据与资料时间；支持安静时段、每日次数上限、同类建议冷却期、关闭某类建议和用户反馈。主动建议与外部动作应分离：从邮件中发现“请付款”只能产生候选，不能直接推导用户批准付款或外发信息。

## 6. 定时和长任务的正确语义

自然语言规则先转换成结构化计划，展示未来三次执行时间。存 IANA 时区与原始语义，分别处理“每 24 小时”和“每天当地 9 点”。出国或修改时区后明确计划跟随哪个时区。安排一个未来时间使用延迟启动；重复执行使用 Schedule。

必须明确重叠策略、补跑窗口、最大运行时间、用户取消和通知行为。Temporal Schedule 具备相关策略；其默认补跑窗口较长，产品不能直接照搬默认值。每日简报适合只补最近一次；外部发送与已经过期的动作不应盲目补跑。暂停计划不会自动中止既有运行，界面需分别表示“暂停计划”和“停止当前任务”。[Temporal Schedule](https://docs.temporal.io/schedule)

任务状态建议：`queued → running → waiting_approval / waiting_connection → succeeded / failed / cancelled / uncertain`。运行记录保留步骤证据、尝试次数、预算、产物和可理解的失败原因。网络断开不等于任务失败；客户端重新打开后应读取持久状态并恢复事件流。

## 7. 外部写入：账本、批准和未知结果

Temporal Activity 可能重复执行；“工作流可靠恢复”并不自动让发送邮件、下单或创建事件只发生一次。外部系统执行成功但 Worker 未收到结果，是必须测试的故障场景。[Temporal Activity 幂等说明](https://docs.temporal.io/activity-definition)

建议执行协议：

1. 模型生成结构化动作提案；服务端校验工具能力和参数。
2. 服务端形成不可变的动作快照：账号、收件人、附件、正文、资源版本、预算、可执行期限。
3. 对需要批准的动作展示预览；批准绑定快照哈希、用户、工具和有效期。参数改变、账号切换、审批过期、源资源变化后重新校验或重新批准。
4. 在本地事务里写入 `OperationLedger` 和出站记录，获取稳定的逻辑 `operation_id`；该 ID 跨基础设施重试保持不变，用户明确要求再做一次时新建 ID。
5. 若供应商支持幂等键或客户端资源 ID，传入稳定值；调用前再次检查授权、撤销状态和并发锁。
6. 持久保存供应商响应和资源 ID，回查实际结果，再报告成功。
7. 遇到超时且无法确定是否写入，进入 `uncertain`，先回查，不能无条件自动重试。

Google Calendar 可由客户端提供符合格式的事件 ID，官方说明它可以避免执行成功后客户端失败引起的重复创建。[Calendar 创建事件](https://developers.google.com/workspace/calendar/api/guides/create-events)

Gmail `messages.send` 文档未提供通用幂等键参数，因此不能假设它与日历有相同保证。可用稳定 Message-ID 和发送记录辅助查询，但把查询结果不足视为未知，而不是证明没有发送。首版优先创建草稿，发送需明确批准；未知结果交给用户核实或受控恢复。[Gmail messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)

周期任务可支持用户授予范围明确的长期批准，例如“工作日 9 点把简报存入指定文件夹”；长期批准应绑定动作模板、目标账号/文件夹、额度和到期时间。用户取消计划或撤销连接器时立即失效。任意动态收件人、交易和永久删除不应被一个笼统的“自动执行”开关放行。

## 8. 连接器不是一次 OAuth 按钮

后台执行需要服务端安全保存可刷新凭据，分离账号身份与实际 scope，按需增量授权，处理刷新失败、用户撤销和重新授权。Google 文档明确离线访问与公开应用的审核要求；敏感/受限 scope 的验证要作为上线关键路径，不能写成最后一天的发布配置。[Google OAuth Web Server](https://developers.google.com/identity/protocols/oauth2/web-server)、[Google OAuth Policies](https://developers.google.com/identity/protocols/oauth2/policies)

Gmail push 是变化提示，不含完整邮件。需保存 `historyId`，处理重复通知并拉取增量；watch 至少每七天续订，官方建议每日续订。应有订阅到期告警、定期对账和事件摄入去重。[Gmail Push](https://developers.google.com/workspace/gmail/api/guides/push)

Gmail 历史游标失效会返回 404，需重新做范围受控的完整同步；Calendar 同步游标失效会返回 410，也需重新同步。同步重建要保留用户删除/忽略语义，不能把所有旧内容再次写成新记忆。[Gmail 同步](https://developers.google.com/workspace/gmail/api/guides/sync)、[Calendar 错误处理](https://developers.google.com/workspace/calendar/api/guides/errors)

连接器统一接口至少包括：授权 scope、读取/写入能力、速率限制、订阅续期、游标、重试分类、幂等策略、数据删除、健康状态。Webhook 必须验证服务商身份或签名，快速确认接收，再异步处理；不能把任何自称 webhook 的请求直接视为用户授权。

## 9. 沙箱与跨设备控制

Playwright 是浏览器自动化工具，不是安全边界。官方默认 Docker 镜像面向测试开发，不推荐用它访问不可信网站；默认 root 会关闭 Chromium sandbox。[Playwright Docker](https://playwright.dev/docs/docker)

生产执行不可信网页和代码，应使用独立沙箱服务或经过验证的 VM/microVM 方案：每运行隔离、非 root、短寿命、禁宿主挂载、CPU/内存/时长/下载上限、出口代理与域名策略、阻断内网和云元数据地址、无长期明文凭据。浏览器会话与用户隔离，截图/录像按敏感产物处理。Firecracker 等方案有宿主机、内核与 seccomp 的持续运维要求，不是引入一个库即可获得隔离。[Firecracker 生产配置](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md)

网页、邮件和文档里的指令按不可信内容处理；模型不能通过检索结果获得系统权限。权限由服务端工具网关执行，不依赖“请不要越权”的提示词。

跨设备需要单独产品线：本地 Companion、设备配对、设备侧常驻服务、短期能力票据、用户可见的连接状态、系统授权、断线恢复、停止开关和升级签名。云端任务不应被等同于控制用户电脑。首阶段可先做 Web/PWA 共享任务状态，后续选择一个桌面系统，再扩展其他系统和移动端。不能假定各移动系统允许持续后台或任意应用控制。

社区技能首版只允许声明式工作流、提示模板和已审核工具组合。任意代码技能、安装依赖、网络访问需要版本固定、权限清单、审查与撤回机制，后置到专门沙箱成熟后。

## 10. 多租户和凭据

PostgreSQL 行级安全适合作为纵深隔离，但超级用户、BYPASSRLS 角色以及默认表所有者可绕过策略。应用运行连接不能拿管理权限；需明确 `FORCE ROW LEVEL SECURITY`、读写策略、后台作业租户上下文和连接池事务边界。[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

数据库隔离之外，向量检索、全文检索、缓存键、对象路径、下载签名、导出、任务队列、通知、追踪和客服调试权限都要绑定租户。对象存储 key 中含 tenant 只便于管理，本身不是授权。用户刷新令牌由 KMS/Secret Manager 保护，经凭据代理按次使用；沙箱拿短期能力或单次请求授权，不能持有整个账户的长期令牌。

## 11. 可测量验收建议

以下是拟定目标，必须经试点基线校准，不能当作已达成指标。

| 维度 | 建议验收方式 |
|---|---|
| 核心闭环 | 五类工作流各 20 个代表用例，明确输入、可用来源和预期产物；端到端成功率 ≥85%，单独报告连接器/模型/权限原因 |
| 事实与引用 | 固定资料集至少 100 问，人工盲评事实正确和来源支持；高风险事实无来源时必须说明无法确认 |
| 记忆 | 已知偏好、矛盾资料、用户纠正、来源过期各有测试；检索不得跨用户，删除后立即不可检索 |
| 删除闭环 | 设定例如 24 小时完成在线副本清理的目标；展示未完成项目；备份另设明确保留期并测试恢复后删除标记有效 |
| 调度 | 10,000 次测试触发，统计开始延迟、漏跑、重复、时区和夏令时；受控负载下建议 p95 启动延迟 ≤60 秒 |
| 写入可靠性 | 在“供应商成功、响应丢失”等位置注入故障；有供应商幂等支持的动作无重复副作用，无可靠回查的动作进入 uncertain |
| 审批 | 改收件人/附件/正文、过期、撤销账号、资源版本变化均不能沿用旧批准；读取外部恶意指令不能扩大权限 |
| 多租户 | 至少 1,000 条越权、导出、任务和签名 URL 用例，零跨租户泄露；检查后台和管理路径 |
| 恢复 | Worker 被杀、网络超时、重复 webhook、游标失效和凭据撤销后，状态可恢复，用户收到可解释结果 |
| 主动性 | 分开统计建议曝光、采纳、误报、重复、关闭通知率；试点看真实用户反馈，不只看生成条数 |
| 经济性 | 每种工作流记录输入/输出 token、模型费、沙箱分钟、搜索、存储和重试倍数；设置每次和每用户月度预算 |

任务“成功”需要同时满足产物正确、权限正确、外部动作结果确认和成本未越界。仅工具返回 200 不足以算成功。

## 12. 工期与成本的现实假设

一个可对外小规模试点的 Web MVP，估计 4—6 名具有 AI 应用与后端经验的核心成员，12—16 周；包括产品/设计、前端、后端/Agent/连接器、质量与安全职责。若已存在成熟平台、仅做演示，周期可缩短；若要覆盖桌面控制、实时语音、技能市场和多端一致体验，应另计约 6—9 个月级别的阶段，而非把全部塞进一个月。上述均为规划估算，不是服务承诺。

建议并行节奏：第 1—2 周冻结五个闭环与验收资料、调研真实界面、申请连接器审核；第 3—6 周交付对话、来源与记忆、读连接器和持久任务；第 7—10 周加入建议、定时、草稿/审批写入、可恢复执行；第 11—14 周做试点、故障演练、越权测试和成本治理；预留 2 周缓冲。OAuth 审核、合作方 API 权限、平台分发许可不包含在可控工期承诺内。

成本应用可替换单价的公式计算：

`月运行成本 = 固定基础设施 + Σ工作流次数 × (输入token/1e6×输入单价 + 输出token/1e6×输出单价 + 工具费 + 沙箱分钟×分钟价 + 搜索费 + 转写/语音费) × 实测重试系数 + 存储/流量/观测 + 第三方审核与合规成本`

`月毛利 = 订阅实收 − 支付/税费 − 月运行成本 − 变动客服支持成本`

工程投入另算 `各岗位人月 × 全成本人月单价`。不要直接用“1000 用户”的总量估算：需要区分活跃用户、付费用户、每活跃用户每天任务数和高耗时浏览器任务占比。

用于预算演算的假设示例：1,000 月活 × 每人每日 3 次任务 × 30 天 = 90,000 次/月；若平均每任务输入 8,000、输出 1,500 token，则约 7.2 亿输入和 1.35 亿输出 token。若 10% 任务浏览器运行 2 分钟，还会产生约 18,000 沙箱分钟。这里没有代入任何供应商报价，真实均值必须用试点数据验证；上下文回放、自动建议与失败重试会显著改变成本。

## 13. 最需要避免的路线遗漏

1. 把三个 API 接通当作连接器完成，漏掉 OAuth 审核、续订、游标失效、速率限制和撤销。
2. 把向量数据库当作全部记忆，漏掉证据、权限、过期、纠正和跨副本删除。
3. 把 Temporal 等同于外部操作 exactly-once，导致重复发送和重复创建。
4. 把 Docker/Playwright 当作生产安全沙箱，或让长期 OAuth 凭据进入执行环境。
5. 用一个通用 Agent 循环承载所有产品逻辑，缺少任务状态、执行账本、预算、取消和恢复协议。
6. 一边做 Web MVP，一边承诺全桌面、全手机、全社区技能能力，造成工期失真。
7. 只验收界面和工具调用次数，不验收真实任务成功、误报、越权、删除和单位成本。
8. 默认用户、数据库、工作流、备份、日志和模型供应商都处于同一个数据生命周期，导致“已遗忘”承诺不真实。

## 14. 对拟议阶段计划的专项审阅

拟议选型“Next.js/React + TypeScript Fastify 模块化单体 + Temporal TypeScript Worker + PostgreSQL/pgvector/全文检索 + S3 + 按需 microVM 沙箱”总体合理。Fastify 是常见且足够的 API 层；本期不需要同时引入另一套复杂 Agent 图编排框架。模型步骤用受控循环与持久 Step 记录，Temporal 负责持久控制流，避免有两个系统同时声称掌管重试和状态。

| 拟议阶段 | 审阅结论 | 建议的可承诺范围 |
|---|---|---|
| P0：6—8 周 beta 核心闭环 | 在严格削减范围下可行，风险中高 | ≤50 名受邀测试；1—2 个连接器读优先；文本/少量文件；有限五个工作流；记忆查看和纠正；调度；外部写入先草稿或明确批准；成本与权限日志。从第一周提交 OAuth 审核，但审核结果不得成为这一节点的隐含保证 |
| P1：9—12 周文档、录音、云浏览器 | 多条独立能力并进容易超载 | 文档先支持 2—3 类格式；录音先上传后异步转写，明确不含完整实时通话；浏览器先公开网页只读/可审查产物，优先托管隔离运行时，不同时自建 microVM 平台 |
| P2：13—20 周桌面、移动分批 | 若指全原生多端或任意控制，则不合理 | 一个桌面操作系统的 Companion，有限文件/窗口能力和用户可见连接状态；移动响应式 Web/PWA 与任务同步。原生 iOS/Android、跨平台桌面、任意第三方应用控制单独估算 |
| 55 类连接器，全量另算 6—12 月 | 量级可以作为方向，不能作为既定上限 | 按“只读检索 / 受控写入 / 实时同步 / 特殊合作资格”分层，先覆盖前 5—10 个高频。某些平台 API 审批、非公开接口和桌面端能力可能无法按统一节奏获取 |

最重要的依赖：先跑通账户、来源权限、任务状态与操作账本，再开放外部写入；先确认沙箱方案再允许执行不可信脚本；先有真实数据和用户反馈再优化主动建议。页面视觉还原可与这些工程工作并行，不能代替它们的验收。

建议在最终路线中同时写两条时间：6—8 周“受邀 beta”与约 12—16 周“可对外小规模 Web 试点”，把质量、支持范围和外部审核依赖讲清楚。4—6 人团队在每一阶段需要至少一位专注前端、一至两位后端/Agent/连接器、一位产品设计，并让测试、安全和运维有明确负责人；如果这些角色全部兼职，需降低并行数和增加缓冲。
