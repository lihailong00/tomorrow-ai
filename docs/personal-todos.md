# 个人事项

任务页使用紧凑的个人事项列表。来源渠道和事项类型分别保存：邮件、通知、对话或手动记录是来源；沟通、学习、运动等是类型。今天、全部、候选、等待和完成的列表均从当前账号的服务端数据读取，不生成演示事项。

## 生命周期

个人事项使用 `suggested`、`pending`、`in_progress`、`waiting`、`completed` 和 `dismissed`。用户收下候选后才进入待办，完成和恢复由用户确认。后台 AI 执行仍使用原有 Task，入口保留为“助手执行记录”，定时计划继续保留。

“准备下一步”创建独立的 `todo_prepare` 后台执行，只生成内容，不运行外部工具。后台执行成功会提供草稿，不会完成个人事项。用户编辑后的草稿不会被迟到的生成结果覆盖。模型配置使用管理后台与部署环境的有效配置；没有可用模型时明确报错，保留事项和来源。

## 资料与授权

`POST /v1/todos/extract` 只接受已保存且属于当前用户的 `conversation` 或 `integration_import` 标识。原文由服务器读取，模型输出严格校验，候选依据必须出现在授权原文中，无法确认的日期留空。同一来源的重复提取保持幂等，忽略的候选不反复出现。

用户可在对话或来源选择页主动发现待办；通知、邮件与分享资料需先确认导入，再整理为候选。读取范围仍受既有连接和设备权限约束，不代表读取微信完整聊天历史或整个短信收件箱。

## 按类型处理

- 沟通事项：准备、修改、分享或复制回复。分享和复制不代表发送；用户确认已经实际回复后，才能记录为等待反馈。
- 学习事项：依据实际目标准备内容，保存笔记和进展，不虚构历史学习数据。
- 运动事项：用户开始、结束并自行记录；可选分钟数为 1–360 的整数，不读取传感器或自动判定完成。
- 其他事项：查看来源，准备资料，或按用户确认记录结果。

当前没有直接发送邮件或第三方应用消息的接口。界面不能把生成草稿、打开应用或唤起分享选择器显示为“已发送”。

## 部署与兼容

客户端和 API、worker 应配套升级。新迁移 `013_todos.sql` 创建独立事项表及提取记录，保留既有任务和计划。SQL 使用 SQLite/PostgreSQL 共用类型和参数方式；实际 PostgreSQL 验收需要单独测试库，SQLite 测试通过不等同于实测 PostgreSQL。

接口包括 `/v1/todos` 的分页列表与创建、`/v1/todos/{id}` 的读取和版本化修改、`/v1/todos/{id}/prepare` 的后台准备，以及 `/v1/todos/extract` 的来源提取。修改携带 `version`，冲突后重新读取再处理；创建和准备复用稳定的 `client_request_id` 避免网络重试导致重复资源。
